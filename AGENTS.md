# PolicyEngine US Agent Instructions

Follow the repository guidance in `CLAUDE.md` for commands, style, changelog entries, and PolicyEngine modeling conventions.

## Test cost and CI capacity

Follow [Test design and CI cost](CLAUDE.md#test-design-and-ci-cost) before adding or expanding tests. Use variable-named YAML tests for policy calculations; reserve Python tests for behavior YAML cannot exercise. Preserve Core/data compatibility and isolation coverage, avoid repeated full-model construction, and do not add CI runners or parallel heavy processes without explicit authorization. Document the purpose and measured cost of new simulation-heavy Python tests in the PR.

## Statutes against forms, instructions and agency practice

When a statute conflicts with a regulation, form, instructions, manual or stated agency practice, follow the statute; forms and instructions fill gaps where the statute is silent. Register the choice and mark the code as [CONTRIBUTING.md](CONTRIBUTING.md#source-conflicts) describes. Never leave it only in a comment or a PR body.

## Partner API contract tests

The YAML files under `policyengine_us/tests/policy/baseline/partners/**` are API partner contract tests. Never rewrite their expected values merely to make CI pass. Follow [Partner API contract tests](CLAUDE.md#partner-api-contract-tests) before you edit any of them. In short:

- Anyone, agents and subagents included, may update an expected value, and a comment in the case that derives it, when: a cited model change in the same PR explains every changed value; the PR body tables every changed value (file, case, variable, old value, new value, cause), computed from every output variable of each affected case, because the test runner stops a case at its first failing variable; you check, failing or not, every case whose name or own comments put it at, just above or just below a value the change moves, including thresholds that formulas compute from moved parameters (compare the parameter trees and those thresholds at the base and the head, since uprating moves values the diff doesn't show); an independent review, by another person or a fresh agent that made neither the model change nor the edits, recomputes each value from the cited source (a rerun of the PR's model doesn't count, though unmoved inputs such as AGI may come from the model at the base) and confirms that the diff changes nothing else in these files without Ziming's approval; and the PR @-mentions Ziming Hua (hua7450, outside a code span, so GitHub notifies him) with the table as an FYI before the review.
- Ziming approves, through the three-question checklist: any edit other than an expected value or a comment that derives it (inputs, name, `period`, error margins, reforms, added or removed cases or output variables); a value change in a case whose purpose the model change defeats, either because a value its name or own comments put it at, just above or just below moves away, or because the change moves it across a threshold it sits on one side of; any changed value the review can't trace; any change to a case marked `# partner-flagged` or named on the PR as one a partner depends on; and any other edit to these YAML files. Ask him, and wait for his approval, before you edit a case you can see falls here. Until he approves a head that contains the edit, the PR doesn't merge, and nobody deletes, skips, renames or loosens a case to turn CI green. A moved boundary case that still passes doesn't hold the PR: leave it as it is and name it in the FYI with proposed inputs. A subagent that reaches one of these cases stops and reports back.
